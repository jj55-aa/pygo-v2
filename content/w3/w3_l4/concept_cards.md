# Git 与协作——项目的时光机

## ⏳ Git 是时光机：建造工地的「存档点」

你走进「建造工地」的中央控制室，工头正盯着墙上贴着的四个大字：**前端、后端、数据库、Git**。他指着最后两个字说：「小子，前面三样是盖楼的材料，这最后一样——是时光机。」

盖楼的人都懂：地基打完要拍照，框架立起来要拍照，每完成一个关键节点都留个影。**后面推倒重来、改崩了，翻出照片就能回到那一刻。** 程序也一样——AI 帮你写代码，改得快、跑偏也快，说不定哪一轮就把项目改乱了。

**Git 就是项目的时光机（版本控制工具）**：它把项目每个关键节点的状态存成一个「存档点」，想回到哪个版本，一键就能回去。存一个版本（commit）**不等于发布了功能**——它只是证明「此刻项目长这样」，相当于打游戏到一个节点先存档，不是说你通关了。

```python
# 模拟 Git 的存档点：把项目状态存进「版本记录」
history = []                     # 版本记录 = 时光机
project = "登录页 v1：能输入账号密码"
history.append(project)          # 第一次存档
project = "登录页 v2：加了记住密码"
history.append(project)          # 第二次存档
print("当前版本：", project)
print("历史存档：", history)
print("想回 v1？", history[0])    # 时光机随时能回到旧存档
```

> ⚠️ 新手最容易踩的坑：
> 1. **存档 ≠ 发布**：commit 一个版本只代表「此刻项目长这样」，不代表功能完整、可以上线——它只是退路，不是成绩单。
> 2. **存档要勤快**：每完成一个小阶段就存一次；等 AI 把项目改乱了才想起存档，已经晚了——连能退回去的稳定点都没有。

## 🧰 命令五兄弟：add / commit / push / pull / status

控制室的墙上挂着一张「命令对照表」，上面是 Git 最常用的五个命令。工头说：**你不需要背命令，但要认得它们各自是干什么的**——因为接下来你要指挥 AI 用它们。

| 命令 | 干什么 | 建造工地比喻 |
| --- | --- | --- |
| `git add` | 把改动装进「暂存区」（告诉 Git 这次要保存哪些文件） | 把要用的材料搬上车 |
| `git commit` | 本地存档：把暂存区的改动存成一个版本 | 给工地拍一张存档照 |
| `git push` | 把本地版本上传到远程仓库（GitHub/Gitee） | 把设计图上传到总部 |
| `git pull` | 从远程仓库拉取最新版本到本地 | 从总部取回最新图纸 |
| `git status` | 查看仓库当前状态：哪些改了、哪些还没提交 | 巡工地：看看哪还没完工 |

记住一句顺口溜：**add 装车 → commit 拍照 → push 上传**；随时 `status` 看一眼。

```python
# 模拟「命令分类器」：用关键词识别命令是干什么的
cmd = input()
if "add" in cmd:
    print("add：把改动装进暂存区")
elif "commit" in cmd:
    print("commit：本地存档")
elif "push" in cmd:
    print("push：上传到远程仓库")
elif "status" in cmd:
    print("status：查看当前状态")
else:
    print("命令不认识，查查对照表吧")
```

> ⚠️ 新手最容易踩的坑：
> 1. **commit 前必须 add**：commit 存的是「暂存区」里的东西——忘了 add，改动根本没上车，拍了照也是白拍。
> 2. **push ≠ commit**：commit 只存在你自己电脑上；想让 GitHub/Gitee 上也有，必须再 push。本地提交可以勤快，远程推送要谨慎。
> 3. **别把「配置远程地址」当 push**：关联远程仓库只是告诉 Git「以后传哪儿」，不等于已经上传。

## 🌿 分支与合并：工地上的并行施工队

工地不只盖一栋楼。东边在加装电梯，西边在改造大门——**两支施工队同时开工，互不干扰**。如果都挤在主楼上乱改，主楼早就塌了。

Git 的**分支（branch）**就是这个道理：

- `main`（主分支）= 主楼：**永远保持稳定**，是能跑的版本
- 新功能 = 一支施工队**拉出警戒线**（开一个分支），在旁边另起炉灶施工
- 施工完毕、**验收合格**，再把成果**合并（merge）**回主楼——主楼瞬间多了一层，还从来没乱过

和 AI 协作时尤其有用：让 AI 在一个新分支上大胆改，改乱了丢掉分支重来，主分支纹丝不动。

```python
# 模拟分支与合并：新功能在分支上施工，做完并回主线
branches = {
    "main": "稳定版：能正常访问",
    "feature-login": "施工中：登录功能",
}
print("主分支：", branches["main"])
print("功能分支：", branches["feature-login"])
# 验收合格，合并回主分支
branches["main"] = "稳定版：含登录功能"
print("合并后主分支：", branches["main"])
```

> ⚠️ 新手最容易踩的坑：
> 1. **别直接在 main 上乱改**：主分支是「稳定版」，新改动先进分支，验收合格再合并——主楼永远不倒。
> 2. **分支干完不等于能合并**：先确认功能没问题、验证通过了，再合并；合并前先想清楚。
> 3. **分支用完记得清理**：不然工地上堆满废弃的警戒线，Git 记录也会越来越乱。

## 🤖 与 AI 协作的 Git 习惯：改前先 commit

工头把最后一条规矩写在最显眼的位置：**「AI 动手前，先把档存了。」**

AI 写得快，跑偏、误改、乱推的速度更快。你越看不懂代码，越不能把希望全押在「AI 下一轮能修好」上——**你得给自己留退路**。正确顺序是：

1. **改前先 commit**：让 AI 动手前，先存一个当前版本的存档点
2. **让 AI 改**：放它去改，随便试
3. **改完先汇报**：让 AI 说明「做了什么、改了哪些文件、验证结果是什么」——先别提交
4. **你验收 → 再 commit**：确认能接受了，才让它把这次改动存成新版本

反过来：AI 试了一堆方案没跑通、改了很多你没让它改的地方——**都先别提交**，先让它解释清楚再说。

```python
# 模拟「改前先存档」检查：开工前确认有存档点
saved = input("开工前存档了吗？(y/n)")
if saved == "y":
    print("有存档点，放心让 AI 改吧")
else:
    print("先 commit 存档，再让 AI 动手！")
```

> ⚠️ 新手最容易踩的坑：
> 1. **别在没提交时让 AI 大改**：改乱了连能退回去的存档都没有——先存档，再动手。
> 2. **commit 信息写清楚**：用大白话说明这次完成了什么（比如「登录页加记住密码」），别写「改了」这种废话。
> 3. **push 前先检查**：密钥、内部资料、账号密码别跟着代码上传——**账号密码也绝不能当普通文字发给 AI**。
