# 独立挑战——建造工地的结业大考

## 🏗️ 项目骨架全景：四大件，一个都不能少

**类比**：在建造工地盖一栋楼，开工前先立起**框架**：地基、承重墙、屋顶、水电管线。没有框架就往上堆砖，墙歪了都不知道。AI 写项目也一样——它开工第一件事不是写某个页面，而是先搭**项目骨架**：把整个工程按职责分好目录。一个完整的项目骨架，由**四大件**组成：

| 四大件 | 工地里的角色 | 放什么文件 |
| --- | --- | --- |
| 前端 | 门面（招牌、菜单、桌椅） | index.html、style.css、app.js |
| 后端 | 账房（处理业务的先生） | app.py、api.py |
| 数据库 | 仓库（存数据的库房） | schema.sql、users.sql |
| 工具 | 工具间（Git 存档、配置文件） | .gitignore、README.md |

**定义**：**项目骨架** = AI 开工时先搭好的目录结构，把「前端、后端、数据库、工具」四大件各归各的目录。四大件齐全，项目才站得稳；缺一件，就像盖楼少了承重墙——后面全是补丁工程。

```python
# 用字典模拟「项目骨架」：四大件各放什么
skeleton = {
    "前端": ["index.html", "style.css", "app.js"],
    "后端": ["app.py", "api.py"],
    "数据库": ["schema.sql", "users.sql"],
    "工具": [".gitignore", "README.md"],
}
for part, files in skeleton.items():
    print(part, "→", len(files), "个文件")
```

> ⚠️ 易错点：
> 1. **骨架 ≠ 功能**：目录搭得再漂亮，里面的页面可能是假的、接口可能是写死的——骨架是「结构」，不代表功能已经做完。
> 2. **四大件别混放**：前端文件丢进后端目录、SQL 脚本扔在根目录，会让 AI 和你自己都找不到北——各归各位，才能快速定位问题。

## 📂 文件归类：按扩展名、按关键词

**类比**：工地上材料成堆：砖头归砖头、钢筋归钢筋、水泥归水泥。分好类，要什么一伸手就能拿。看 AI 写的项目也一样——**拿到一个陌生文件，先归类，再细看**。归类有两种依据：

**按扩展名**：`.html` / `.css` / `.js` → 前端；`.py` → 后端；`.sql` → 数据库。
**按关键词**：说明里含 `html/css/js/页面` → 前端；`py/接口/处理` → 后端；`sql/表/数据` → 数据库；`git/配置` → 工具。

**定义**：**文件归类** = 按扩展名或说明里的关键词，把文件分到「前端/后端/数据库/工具」四类里。扩展名最可靠（`x.py` 一定是 Python），关键词适合说明里没写扩展名的情况；两个都用上，几乎不会认错。

```python
# 按关键词给一行「文件名,说明」归类
def classify(line):
    if any(k in line for k in ["html", "css", "js", "页面"]):
        return "前端"
    if any(k in line for k in ["py", "接口", "处理"]):
        return "后端"
    if any(k in line for k in ["sql", "表", "数据"]):
        return "数据库"
    if any(k in line for k in ["git", "配置"]):
        return "工具"
    return "未知"

for f in ["index.html,首页页面", "app.py,处理接口", "data.sql,用户表", ".gitignore,git 配置"]:
    name, desc = f.split(",")
    print(name, "→", classify(f))
```

> ⚠️ 易错点：
> 1. **关键词会撞车**：`admin.py,后台页面管理` 里既有 `py`（后端）又有 `页面`（前端）——要定一个判断顺序（前端 → 后端 → 数据库 → 工具），先命中哪个算哪类，程序才不会前后矛盾。
> 2. **别硬归类**：四类关键词一个都不沾的文件，老老实实标「未知」，别硬塞进某一类——硬归类比不归类更容易误导人。

## 🔍 从骨架看项目：先看目录，再看逻辑

**类比**：第一次进一栋新楼，你是先挨个房间敲门，还是先看大厅里的楼层示意图？当然是先看**楼层图**——几层楼、每层是干嘛的，心里有数再进房间。看 AI 写的项目也一样，顺序是：**先看目录，再看逻辑**。

**定义**：**从骨架看项目** = 拿到一个 AI 项目，按三步走：① 看**根目录**（README、配置文件——项目是干嘛的、怎么启动）；② 看**四大件目录**（前端/后端/数据库/工具各自有什么文件）；③ 再深入**入口文件**和**业务逻辑**（比如 app.py 里真正的接口怎么写的）。目录是地图，逻辑是房间——先地图后房间，才不会一头扎进细节里迷路。

```python
# 第一步：看目录（地图），不急着看代码
tree = [
    "项目/",
    "├─ 前端/   index.html  style.css  app.js",
    "├─ 后端/   app.py  api.py",
    "├─ 数据库/ schema.sql  users.sql",
    "└─ 工具/   .gitignore  README.md",
]
for line in tree:
    print(line)
```

> ⚠️ 易错点：
> 1. **一上来就翻代码**：AI 生成的项目可能有几百个文件，直接钻进某个 .py 里，半小时后你都不知道自己在看哪一层——先花两分钟看目录，省下两小时。
> 2. **只看名字不看内容**：`app.py` 名字像入口，打开一看可能只是空壳；目录看的是「结构」，关键逻辑还得进文件确认。

## ✅ 综合验收：四件套各就各位了吗

**类比**：工地封顶前要**验收**：承重墙够不够、水电通不通、消防过不过。验收不过，住进去迟早出事。AI 交项目也一样——别急着夸「能跑」，先做一次**骨架验收**：四大件齐不齐、文件归类对不对、入口清不清楚。

**定义**：**综合验收** = 拿到 AI 项目后按清单检查：① 四大件（前端/后端/数据库/工具）是否**齐全**；② 关键文件（入口 .py、页面 .html、数据 .sql）是否**归类正确**；③ 能不能**快速定位**到「页面在哪、接口在哪、表在哪」。三项都过，骨架健康，才敢让 AI 继续往下写功能；哪项不过，先让 AI 把骨架收拾利索。

```python
# 验收清单：四大件各就各位了吗？
skeleton = {"前端": 3, "后端": 2, "数据库": 1, "工具": 2}
for part in ["前端", "后端", "数据库", "工具"]:
    n = skeleton[part]
    print(part, "→", "✓ 就位" if n > 0 else "✗ 缺失")
```

> ⚠️ 易错点：
> 1. **「能跑」≠「验收通过」**：页面能打开可能只是写死的假数据——骨架验收看的是结构（四大件、归类、定位），不是「看起来能跑」。
> 2. **验收要趁早**：骨架期发现缺数据库目录，改起来就几行；等 AI 写了几百行功能才发现，就是推倒重来——骨架验收放在开发前，不是上线前。
