# 后端业务——看懂 AI 写的后端

## 🧮 后端在做什么——建造工地的「账房先生」

走进建造工地，你会看到三拨人：**前端**是「接待大厅」——用户能看到的页面、按钮、输入框，负责让用户操作；**数据库**是「材料仓库」——砖头水泥、账本数据都堆在那里，负责存数据；而**后端**是藏在后屋的「账房先生」——用户看不见他，但每一件事能不能办、该怎么办，都是他说了算：

- 能不能进工地 → 登录校验（密码对不对、账号有没有被封）
- 订的货发不发得出去 → 库存够不够
- 这笔账算得对不对 → 价格、优惠券、满减

**定义**：后端 = 藏在产品背后的**业务处理层**。它接收前端的请求 → 校验数据 → 做业务判断 → 读写数据库 → 把结果返回给前端。用户看不见它，但产品的"规矩"全在它这儿。

```python
# 模拟：前端收表单，后端做判断（账房先生说了算）
user = {"name": "阿强", "password": "123456"}

name = "阿强"
pwd = "123456"

if name == user["name"] and pwd == user["password"]:
    print("登录成功，放行！")
else:
    print("登录失败：账号或密码不对！")
```

> ⚠️ 易错点：
> 1. **前端能判断 ≠ 后端不用判断**：前端是用户能碰到的地方，可以被绕过或篡改，真正关键的判断必须放在后端。
> 2. **后端 ≠ 数据库**：数据库只负责存数据，判断和处理是后端的事，别把两者混成一个。
> 3. **后端 ≠ 网络**：网络只负责把数据传来传去，不负责业务。

## 🗺️ 看懂后端骨架——路由 → 函数 → 返回 JSON

账房先生不是一个人在干活，他前面挂着一块「办事窗口清单」：每个窗口一块牌子（**路由**，比如 `/api/login`），牌子上写着"办什么事"（**接口**）；窗口后面坐着一位办事员（**处理函数**）；办完事，办事员把一张回执单递给你——这就是**返回的 JSON**（结构化数据）。

看懂 AI 写的后端骨架，只要找齐这三件套：

| 骨架零件 | 是什么 | 例子 |
| --- | --- | --- |
| 路由 | URL 地址，前端请求的"入口" | `/api/login` |
| 处理函数 | 干活的具体代码 | `def login(): ...` |
| 返回 JSON | 给前端的结构化结果 | `{"ok": true, "msg": "登录成功"}` |

**定义**：后端骨架 = 路由（入口）→ 处理函数（业务）→ 返回 JSON（结果）。真实框架（比如 Flask）用装饰器写路由，这里我们用字典模拟同一套套路：

```python
# 模拟后端骨架：路由表 + 处理函数 + 返回 JSON
routes = {
    "/api/health": "health",
    "/api/login": "login",
    "/api/orders": "list_orders",
}

def login():
    return {"ok": True, "msg": "登录成功"}

# 前端请求 /api/login：先查路由 → 再调函数 → 拿到 JSON
path = "/api/login"
func_name = routes[path]     # 路由表：地址 → 函数
print("路由对应的函数：", func_name)
result = login()             # 调用处理函数
print("接口返回 JSON：", result)
```

> ⚠️ 易错点：
> 1. **路由只是入口地址**：接口背后的业务判断才是重点，看懂骨架别只盯着 URL。
> 2. **返回的 JSON 通常是字典（键值对）**：`{"ok": True}`，不是随便 print 一句话。
> 3. 真实框架的路由写法（`@app.route('/api/login')`）和这里不一样，但"路由 → 函数 → 返回"的套路是一样的，认得出来就行。

## 🧠 业务逻辑——if 判断、循环、计算

账房先生干活有一整套「工地规矩」：满 100 减 20、库存不够不许下单、只有管理员才能删帖子……这些规矩落到代码里，就是**业务逻辑**。它主要靠三样东西：

- **if 判断**：这件事能不能做（库存够不够、有没有权限）
- **循环**：批量处理（遍历订单、逐个校验）
- **计算**：算得对不对（总价、折扣、找零）

**定义**：业务逻辑 = 产品规则在代码里的实现。看懂 AI 写的后端，大部分时间就是在读它的 `if`、`for` 和算术运算——它们不神秘，就是把"规矩"翻译成代码。

```python
# 模拟后端「下单接口」的业务逻辑
price = 88      # 单价
stock = 5       # 库存

num = 2         # 用户买 2 件

if num > stock:              # 规矩 1：库存够不够
    print("不通过：库存不足！")
else:
    total = price * num      # 规矩 2：算总价
    if total >= 100:         # 规矩 3：满 100 减 20
        total = total - 20
    print("通过：应付", total, "元")
```

> ⚠️ 易错点：
> 1. **判断顺序很重要**：先查库存再算钱，顺序反了会出错（库存不足还报"通过"）。
> 2. **别把业务逻辑堆在路由层**：路由只负责"接客"，规矩写在处理函数里。
> 3. **循环也是业务逻辑**：批量校验、遍历订单、统计数量，都靠 `for`。

## ✅ 验收后端——能跑通，数据对

工地验收员从不"听人说"：AI 说"做好了"不算数，得**拿证据**。验收员拿一张验收单（测试用例），挨个接口去"打"（发真实请求），只盯两件事：

1. **能不能跑通**：不报错、有返回结果
2. **数据对不对**：实际返回的和期望值一致

**定义**：验收后端 = 用真实请求打接口，把「实际响应」和「期望结果」做比对：能跑通 + 数据对 = **通过**；否则就是**不通过**。听不懂的地方就让 AI 拿出实际运行结果，别只听一句"已完成"。

```python
# 模拟验收员：接口名 → 正确响应（期望值）
expect = {
    "/api/health": "ok",
    "/api/login": "登录成功",
}

actual = "ok"   # 假设这是接口实际跑出来的结果

if actual == expect["/api/health"]:
    print("通过")
else:
    print("不通过：实际=" + actual)
```

> ⚠️ 易错点：
> 1. **能跑通 ≠ 通过**：接口返回了但数据不对（登录失败却说"成功"），照样不通过。
> 2. **别只听 AI 说"已完成/已优化"**：要它给出实际运行结果当证据。
> 3. **比对用 `==`**：实际值和期望值要完全一致，包括中文内容。
