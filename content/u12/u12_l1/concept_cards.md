# SQLite 入门——数据地堡的第一把钥匙

## 🗄️ 数据库：数据的地堡

想象你一路闯关攒下的宝物都装在**随身口袋**（变量、列表、字典）里——口袋确实方便，但**程序一关，口袋就消失，宝物全没了**。游戏公司几百万玩家的账号、金币，总不能每次关服就清零吧？这时候就需要**数据库（Database）**出场了。

**数据库就是专门存数据的地堡**，它比随身口袋和 Excel 都厉害：

- **长期保存**：程序关了，数据还在
- **快速查询**：几百万行也能秒查
- **多人安全读写**：好多人同时存取，数据不错乱

地堡里的数据怎么摆放？和你见过的 Excel 表格长得一模一样——**表 + 行 + 列**：

| 档案ID | 姓名 | 等级 |
| --- | --- | --- |
| 1 | 剑圣 | 50 |
| 2 | 奶茶猫 | 32 |

- **表（Table）**：放同一类数据的容器，比如「玩家档案表」
- **行（Row）**：表里的一横行 = **一条记录**（一个玩家的完整信息）
- **列（Column）**：表里的一竖列 = **一个字段**（所有玩家都有「等级」这个属性）

> 🏷️ 记忆口诀：**表 = 一摞成绩单，行 = 一张成绩单，列 = 成绩单上的一个项目**。

Excel 也能做表格，为什么还要数据库？因为文件一多 Excel 就卡成蜗牛、几万人同时改会乱套、想查「所有 40 级以上的玩家」只能肉眼翻。这些活，数据地堡都能干。

在 Python 里，用**字典 + 列表**就能模拟一张表：

```python
# 字典 = 一行记录（字段名就是列名）
rec1 = {"id": 1, "name": "剑圣", "level": 50}
rec2 = {"id": 2, "name": "奶茶猫", "level": 32}

# 列表 = 一张表（装多行记录）
records = [rec1, rec2]

# 模拟查询：找出等级 >= 40 的档案
for rec in records:
    if rec["level"] >= 40:
        print(rec["name"], rec["level"])   # 剑圣 50
```

> ⚠️ 新手最容易搞混：
> 1. **行 = 记录，列 = 字段**，千万别记反：一行是一个人的完整信息，一列是所有人在同一个属性上的值。
> 2. 变量里的数据程序一关就没了；**数据库的使命就是长期保存**——这是它和普通文件、变量的根本区别。

## 🗣️ SQL 四大家族：地堡的四种口令

地堡大门前有位守门人，只听得懂一种语言——**SQL（Structured Query Language，结构化查询语言）**。想取档案、改档案，都得用 SQL 跟它说话。

SQL 语句按功能分成**四大家族**：

| 家族 | 全称 | 管什么 | 代表命令 |
| --- | --- | --- | --- |
| **DDL** | 数据定义语言 | 定义表结构：建表、删表 | `CREATE`、`DROP` |
| **DML** | 数据操作语言 | 增删改**数据** | `INSERT`、`UPDATE`、`DELETE` |
| **DQL** | 数据查询语言 | 查数据（只读） | `SELECT` |
| **DCL** | 数据控制语言 | 权限控制 | `GRANT` |

记法：**「定、改、查、权」**——DDL 定结构，DML 改数据，DQL 查数据，DCL 管权限。

一条查询语句长这样：`SELECT name, level FROM players WHERE level >= 40;`——从 `players` 表里取出等级 ≥ 40 的姓名和等级。

用 Python 模拟同样的查询：

```python
players = [
    {"player_id": 1, "nickname": "剑圣", "level": 50},
    {"player_id": 2, "nickname": "奶茶猫", "level": 32},
]
# 模拟 SELECT name, level WHERE level >= 40
for p in players:
    if p["level"] >= 40:
        print(p["nickname"], p["level"])   # 剑圣 50
```

> ⚠️ 新手最容易搞混：
> 1. **SQL 关键字习惯大写**：`SELECT`、`FROM`、`WHERE` 大写只是书写习惯（大小写都能跑），真正要分清的是**四个家族各管什么**。
> 2. **DQL 只管查询**：增、删、改是 DML 的活，别把 `SELECT` 归进 DML。
> 3. `WHERE` 是查询里的**过滤条件**，不是查询动作本身——「查询」这个动作的关键字是 `SELECT`。

## 🪶 SQLite：轻量级嵌入式王者

地堡也有大小之分。有的地堡（比如 MySQL）得单独雇一个**守门人服务器**：先安装、再启动服务，才能存取数据。而 **SQLite** 是**嵌入式**地堡——**整个数据库就是一个小文件**（比如 `bunker.db`），零配置、不用装服务器，程序拿着文件就能读写。

- **一个文件 = 整个数据库**：把文件拷走，就等于搬走了整个地堡
- **免安装、零配置**：不需要装软件、不需要启动服务
- **Python 自带**：真实环境里 `import sqlite3` 就能用，无需额外安装
- **随处可见**：手机 App、浏览器、各种小工具都在用 SQLite

为什么先学它？因为它是**最轻的上手方式**——不用折腾环境，先把「数据库的思考方式」练熟，以后再学 MySQL 这类大家伙，不过是换一把大钥匙的事。

```python
# 真机环境里：import sqlite3 就能操作 SQLite
# 本课判题环境没有 sqlite3 模块，所以我们用字典模拟 SQLite 文件里的一张表
bunker = [
    {"id": 1, "name": "剑圣", "level": 50},
    {"id": 2, "name": "奶茶猫", "level": 32},
]
for row in bunker:            # 模拟 SELECT *：把整张表读出来
    print(row["id"], row["name"], row["level"])
```

> ⚠️ 新手最容易踩的坑：
> 1. **SQLite 是文件，不是服务器**：它没有独立的服务进程，不存在「启动 SQLite 服务」这回事。
> 2. **本课判题环境（Pyodide）里没有 sqlite3，也没有 MySQL**——所以本课统一用**列表 + 字典模拟表**，把「数据库的思考方式」练熟，真机环境再上真 SQLite。

## 🔑 主键：每行档案的身份证号

档案表里可能有两个人都叫「小明」，怎么区分它们？靠**主键（Primary Key）**——一个能**唯一标识每一行**的字段，就像每行档案的**身份证号**。

```python
# 档案表：id 是主键，每个档案的 id 独一无二
records = [
    {"id": 1, "name": "小明", "level": 10},
    {"id": 2, "name": "小明", "level": 20},   # 重名没关系，id 不同就行！
]
```

主键有两条**铁规矩**：

1. **不能重复**——一张表里不能出现两个相同的 id
2. **不能为空**——每一行都必须有主键值

日常里的主键到处都是：身份证号、学号、订单号……都是「一条记录一个号」。所以**昵称、等级、金币都当不了主键**——会重名、会相同；只有唯一且非空的 id 才合格。

> ⚠️ 新手最容易踩的坑：
> 1. **主键 = 唯一 + 非空**，两条铁规矩缺一不可。
> 2. 别拿**昵称**当主键：两个玩家都能叫「小明」，一重复就分不清谁是谁了。
