# 部署流程——把代码送上线

## 🚀 部署是发射：点火才是见真章

你站在「发射台」的控制塔里。脚下的火箭——你的项目——已经在厂房里试车无数次了：功能正常、页面能开、本地跑得欢。指挥官却一直不按发射键：「试车只是在地面测试，**点火把火箭送上天，才是见真章。**」

**部署（deploy）就是那一下点火**：把只在你自己电脑上能跑的代码，搬到一台**永远开机、永远联网的服务器**上，让它跑起来、对外提供服务。为什么必须搬？因为 `localhost:3000` 里的 `localhost` 指的是「我自己这台电脑」——你发给朋友，他浏览器找的是他自己的电脑，当然什么都打不开。部署之后，地址变成服务器的公网 IP，全世界的用户都能访问。

```python
# 模拟「部署」：把代码从本地送上服务器
def deploy(code):
    print("点火！把代码送上服务器……")
    server = code          # 服务器开始运行这份代码
    return server

local_code = "火箭指挥系统 v1.0"
print("本地试车成功：", local_code, "（只有你自己能访问）")
online = deploy(local_code)   # 部署 = 把代码放到服务器上跑起来
print("部署完成：", online, "（全世界都能访问了）")
```

> ⚠️ 新手最容易踩的坑：
> 1. **本地跑通 ≠ 上线**：`localhost` 只有你自己打得开；代码没上服务器，用户就永远看不到。
> 2. **内网穿透的临时链接不算部署**：电脑一关链接就没了，那只是「演示」，不是「上线」。

## 🧱 部署五步：上传 → 装依赖 → 启动 → 开端口 → 验证

点火不是按一个键就完事，发射台有一整套标准流程。部署也有固定的五步，**顺序不能乱**：

| 步骤 | 干什么 | 发射台比喻 |
| --- | --- | --- |
| ① 上传 | 把本地代码传到服务器 | 把火箭从厂房运到发射台 |
| ② 装依赖 | 安装项目运行需要的软件包（`pip install`） | 加注燃料、装好设备 |
| ③ 启动 | 把程序真正跑起来 | 点燃引擎 |
| ④ 开端口 | 放行防火墙/安全组，让外部能访问 | 打开发射窗口 |
| ⑤ 验证 | 用浏览器从外面访问，确认能打开 | 确认火箭真的上天了 |

**第 ⑤ 步验证是灵魂**：很多人到第 ④ 步就收工了，结果用户一访问就 502。部署完成的标准不是「我以为好了」，而是「我真的从外面访问通了」。

```python
# 模拟部署五步：一个不能少，顺序不能乱
steps = ["上传", "装依赖", "启动", "开端口", "验证"]
print("部署五步：", " → ".join(steps))
for i, s in enumerate(steps, 1):
    print(f"第{i}步：{s}")
```

> ⚠️ 新手最容易踩的坑：
> 1. **顺序不能换**：没装依赖就启动，程序一跑就报「找不到模块」；没开端口就验证，外面根本进不来。
> 2. **别漏「验证」**：装完、启动完、端口开了，一定要亲自从外面访问一次——那才是「上线成功」的唯一证据。

## 📦 Docker 是什么：集装箱思维

港口里运货有两种方式：把货物拆散了一件件搬上船（麻烦，还容易漏）；或者**提前把货装进标准集装箱**，吊车一吊就走，到哪个港口都能直接卸下来用。

- **原生部署** = 拆散搬货：在每台服务器上现场装环境、装依赖，一件件来
- **Docker** = 集装箱：把**代码 + 运行环境 + 依赖**提前打包成一份标准模板，搬到哪台机器都能「开箱即用」

Docker 的三个词，用集装箱理解就通了：

| Docker 术语 | 集装箱比喻 | 是什么 |
| --- | --- | --- |
| **镜像（Image）** | 集装箱的模板/图纸 | 打包好的「环境+代码」标准模板 |
| **容器（Container）** | 箱子真正吊上船跑起来 | 镜像运行起来的实例（本质是一个进程） |
| **数据卷（Volume）** | 箱子外的固定仓库 | 数据存在容器外，容器删了数据不丢 |

镜像解决了「在我电脑上明明能跑」的千古难题：环境和代码一起打包，到哪台服务器都是同一套。但注意——**Docker 不是免维护**：数据存哪、开了哪些端口、怎么回退，全藏在启动命令背后，出了问题排查起来反而更黑。

```python
# 模拟 Docker：镜像（模板）→ 容器（运行实例）
image = {"代码": "火箭指挥系统", "环境": "Python 3.11", "依赖": "已装好"}
print("镜像（集装箱模板）：", image)
container = image.copy()          # 容器 = 镜像跑起来的实例
print("容器（跑起来了）：", container)
print("换一台服务器？照镜像重建容器，环境一模一样")
```

> ⚠️ 新手最容易踩的坑：
> 1. **别把「一键启动成功」当「部署完成」**：容器起来了，不等于数据不会丢、端口没乱开、能回退——三件事都得确认。
> 2. **数据一定要放容器外**：数据库、用户上传的文件如果存在容器里，容器一删/重建，数据跟着一起消失。

## 🚧 避坑与日志：两道大门 + 一个黑匣子

部署卡壳时别慌，90% 的新手坑就三类——**报错停下、端口被占、门没开**。

- **防火墙 + 安全组 = 两道大门**：云厂商后台的「安全组」和服务器系统自己的「防火墙」是两道独立的大门，**缺一道外部就访问不了**。装了半天访问打不开？八成不是没装好，是门没开。
- **端口被占**：你的程序想用 8080，可 8080 早被别的程序占着——服务怎么都起不来。查一下占用，换个端口或停掉那个程序就行。
- **看日志 = 找黑匣子**：程序挂了、起不来，第一件事不是瞎猜，是**看日志**。日志会老老实实记下它死在哪、为什么死——把日志原样复制给 AI，它能一眼看出毛病。

```python
# 模拟避坑排查 ①：端口被占用，服务起不来
used_ports = [80, 443, 8080]
port = 8080
if port in used_ports:
    print("端口 8080 被占用，启动失败！")
    print("排查：换一个端口，或停掉占用它的程序")
else:
    print("端口空闲，服务启动成功")

# 模拟避坑排查 ②：看日志找原因
log = "2026-05-01 10:00:03 ERROR 数据库连接失败: 密码错误"
if "ERROR" in log:
    print("日志里发现报错：", log.split("ERROR ")[1])
    print("把这段日志原样发给 AI，让它告诉你怎么修")
```

> ⚠️ 新手最容易踩的坑：
> 1. **别只开一道门**：安全组放行了、系统防火墙还拦着，照样访问不了；两道大门都要检查。
> 2. **别瞎猜乱改**：部署出问题，唯一动作是「把报错/日志原样复制发给 AI」——自己瞎猜乱改，只会越弄越乱。
> 3. **日志是排查的命根子**：别把日志随手删了；上线后项目出问题，全靠它救命。
