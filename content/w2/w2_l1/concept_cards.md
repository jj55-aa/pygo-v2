# 需求讨论——立项大厅的第一张图纸

## 🏗️ 需求是地基：立项大厅的第一张图纸

你走进了「立项大厅」——这里是所有 AI 项目开工前必经的第一站。大厅正中央挂着一幅巨型海报，上面只有一句话：

**「房子塌不塌，看地基；项目烂不烂，看需求。」**

建房子要先画图纸、打地基，再往上砌砖。做项目也一样（尤其是和 AI 一起 Vibe Coding）：**第一步不是写代码，而是把需求聊清楚**。很多人脑子里刚冒出一个想法，就急着对 AI 说「帮我做个项目」，AI 立刻开写——看起来效率很高，实际上很危险：

- 一旦方向错了（数据结构错、页面流程错、功能边界错），就不是改几行代码的事，而是**整个地基重来**
- 重来的时候，AI 往往不会干净利落地重来——它会留下一堆死代码、到处打补丁，把项目结构越改越乱

所以立项大厅的第一条规矩：**动手前先聊需求**。聊清楚 = 给项目打地基。把聊出来的内容记进一张「需求卡」，项目就有了可以回看的依据：

```python
# 模拟立项大厅的「需求地基检查」
project = {
    "是什么": "给奶茶店做点单小程序",
    "给谁用": "奶茶店顾客和店员",
    "解决什么": "排队点单太慢",
    "怎么算成功": "顾客扫码后 1 分钟内完成点单",
}
for key, value in project.items():
    print(key, "：", value)
```

> ⚠️ 新手最容易踩的坑：
> 1. **立项 ≠ 写代码**：立项阶段要让 AI 当「产品合伙人」，不是「代码生成器」——聊清楚之前，明确告诉 AI「先别写代码」。
> 2. **需求聊不清楚就开工，是项目烂尾的头号原因**：返工的成本，永远比讨论的成本高得多。

## ❓ 需求三问：给谁用、解决什么、怎么算成功

大厅的接待员接待每一位想立项的人，开口就是**三连问**——这就是大名鼎鼎的**需求三问**：

| 问题 | 例子（奶茶店点单小程序） |
| --- | --- |
| ① 给谁用？ | 奶茶店顾客（扫码点单）、店员（收单出杯） |
| ② 要解决什么问题？ | 高峰期排队太久、店员记错单 |
| ③ 怎么算成功？ | 顾客扫码后 1 分钟内能下完一单 |

AI 可以帮你写代码、查资料、补盲区，但它**不能替你决定你真正想做什么**。这三个问题如果自己都没想清楚，AI 只能靠猜——猜出来的，多半不是你要的。

用代码做一张「需求三问填空卡」，把聊到的答案记下来：

```python
# 立项大厅的「需求三问」填空卡：读入三行，依次回答三个问题
need = {
    "给谁用": input(),
    "解决什么": input(),
    "怎么算成功": input(),
}
for q, a in need.items():
    print(q, "：", a)
```

> ⚠️ 新手最容易踩的坑：
> 1. **别替用户做决定**：AI 说「我觉得应该加个会员系统」时，先反问自己——用户真的需要吗？需求的主角是用户，不是你的想象，更不是 AI 的脑补。
> 2. 三问不是考试题，是**聊天的开场**：答案越具体，后面的代码越不容易跑偏；答案越模糊，AI 越容易自由发挥。

## 🗣️ 模糊 → 具体：从「做个网站」到「奶茶店点单小程序」

接待员最怕听到的一句话就是：「我想做个网站。」

「做个网站」只说了**形式**，什么都没说清楚：网站给谁用？解决什么问题？怎么算成功？全都得靠 AI 脑补——而 AI 脑补出来的，往往不是你要的。

把模糊需求改写成具体需求，是立项的第一项基本功：

|  | 模糊需求 | 具体需求 |
| --- | --- | --- |
| 原话 | 「我想做个网站」 | 「给奶茶店做点单小程序」 |
| 给谁用 | ？ | 顾客扫码点单、店员收单 |
| 解决什么 | ？ | 高峰期排队太慢 |
| 怎么算成功 | ？ | 顾客 1 分钟能下完一单，第一版先支持 3 款招牌奶茶 |

用代码模拟一次「需求体检」：读入一句话需求，看看它有没有提到「用户」——没有用户线索，多半是模糊需求，先别急着开工：

```python
# 模拟需求体检：一句话需求里有没有「给谁用」的线索
req = input()
if "店" in req or "顾客" in req or "用户" in req:
    print("有用户线索，继续追问具体场景吧")
else:
    print("太模糊了！先问清楚：给谁用？")
```

> ⚠️ 新手最容易踩的坑：
> 1. **需求 ≠ 功能清单**：需求先讲「问题」（给谁用、解决什么、怎么算成功）；功能是后面拆出来的「解决方案」。一上来罗列「要有登录、要有会员、要有优惠券」，却说不出要解决什么问题，等于还没聊清楚。
> 2. **「做个网站」「做个 App」说的是形式，不是需求**：形式背后要解决的问题，才是需求本身。

## ✅ 验收标准：做完怎么算好

聊完需求三问，还差最后一条：**怎么算做完？**——这就是**验收标准**。

验收标准的关键词是**可测量**：有数字、有动作、能检查。

- ❌ 不可测量：「做得快一点」「好用就行」「差不多就行」
- ✅ 可测量：「顾客扫码后 30 秒内能完成点单」「3 台手机同时点单不报错」「店员能按订单号查到每一笔订单」

立项文档里专门有一栏「验收规则」：**第一版做到什么程度才算完成**。记住——**不是 AI 说完成就完成**，而是要有可以检查的标准。没有验收标准，AI 会永远「还差一点」，项目无限期烂尾。

用代码模拟一次「验收检查」：读入一句验收标准，看看它是不是可测量的：

```python
# 模拟验收检查：这句话能当验收标准吗？
criteria = input()
fuzzy = ["快", "好", "差不多", "方便"]
too_vague = False
for word in fuzzy:
    if word in criteria:
        too_vague = True
if too_vague:
    print("太模糊了，请换成可测量的标准")
else:
    print("这个标准可以验收！")
```

> ⚠️ 新手最容易踩的坑：
> 1. **验收标准必须可测量**：「快一点」「好一点」没法检查；「30 秒内」「能打印小票」才行。
> 2. **验收标准要在动手前定好**：做完再定，你会说「不行」，AI 会说「差不多行了」——各说各话，项目就烂在验收这一关。
