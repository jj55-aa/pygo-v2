# 项目计划与保险——不烂尾的保障

## 🧭 开发全流程七步：立项大厅的"路线图"

你站在「立项大厅」中央，抬头看见大厅墙上挂着一张巨大的**路线图**。管理员告诉你：盖楼不能先装修，项目不能先写代码——**每一步都有固定的顺序，跳步就要返工**。

这面墙上的路线图，就是开发一个项目的**完整流程（七步）**：

| 步骤 | 干什么 | 类比（盖楼） |
| --- | --- | --- |
| 立项 | 想清楚项目要做什么，和 AI 把需求聊明白 | 想清楚要盖什么楼 |
| 文档 | 把需求、功能、计划写下来 | 画施工图纸 |
| 骨架 | 搭一个能跑起来的最小架子 | 打地基、立框架 |
| 开发 | 一个功能一个功能地写 | 一层一层往上盖 |
| 测试 | 把功能跑一遍，查问题 | 竣工验收检查 |
| 部署 | 把做好的项目放到服务器上 | 通水通电 |
| 上线 | 让用户用上项目 | 开门营业 |

用代码把这张路线图"贴"进编辑器，跑一跑：

```python
# 立项大厅墙上的"开发路线图"
roadmap = ["立项", "文档", "骨架", "开发", "测试", "部署", "上线"]
for i, step in enumerate(roadmap, 1):
    print(i, "→", step)
```

> ⚠️ 新手最容易踩的坑：
> 1. **顺序不能乱**：没立项就急着让 AI 敲代码，它只能靠猜，后面必然返工。
> 2. **别跳过测试直接上线**：不验收就放出去，bug 会全堆到用户面前。
> 3. **上线不是终点**：上线后还有运维、备份、迭代，路线图会继续延伸。

## 📜 立真源与落文档：文档先行

路线图有了，还得把每一步画成**施工图纸**。立项大厅的墙上贴着四个大字：**立真源，落文档**。

- **真源文档（Single Source of Truth）** = 这一阶段唯一的"可信来源"：做什么、做到什么程度、怎么验收，都写清楚
- **AI 是照文档干活的**：有文档，它不脑补；没文档，它就自由发挥——写着写着脱离计划，这叫**漂移（Drift）**
- **聊天里临时冒出来的好主意**：不是不能改，但必须**回写进文档**才算正式变更，口头说说 AI 转头就忘

一句话：**先落文档，再写代码**。文档是方向，AI 照着走，你照着验收。

用代码模拟一次"开工前检查"：

```python
# 模拟：开工前对照"落文档"检查单
doc_ok = True    # 需求文档写好了
plan_ok = True   # 阶段计划拆好了
if doc_ok and plan_ok:
    print("文档齐了，可以开工！")
else:
    print("还缺文档，先别让 AI 写代码")
```

> ⚠️ 新手最容易踩的坑：
> 1. **只动嘴不动手**：聊完不落文档，等于没聊——AI 只能靠猜。
> 2. **文档和代码越走越偏**：AI 改了哪里，文档要及时更新，图纸过期就管不住它了。
> 3. **一次只拆当前阶段**：别提前把后面所有阶段都细化——需求会变，提前细化大半白做。

## 🛡️ 项目保险：备份 / 版本控制 / 里程碑

大厅角落里摆着一台游戏机。管理员说：打 BOSS 之前，先**存档**——打赢了继续走，打输了从存档点还原。**项目也一样，要买「不烂尾保险」**，三个险种缺一不可：

| 险种 | 是什么 | 防什么 |
| --- | --- | --- |
| 备份 | 把代码复制到别处（网盘、远程仓库） | 电脑坏了、文件丢了 |
| 版本控制（Git） | 像游戏存档：记录每次重要变化，AI 改乱了随时**回退** | AI 大改把项目改坏 |
| 里程碑 | 把大项目切成一个个阶段目标（骨架搭好、登录完成……） | 闷头做到底，中途失控 |

Git 有个关键习惯叫**阶段提交**：每完成一个**能正常运行**的阶段，就提交一次版本记录——不是每改一行就提交，也不是攒到最后才提交。

用代码模拟一次"里程碑检查"：

```python
# 模拟：里程碑检查（能正常运行才算数）
def check_milestone(done, can_run):
    if done and can_run:
        return "里程碑达成，提交一次版本记录！"
    return "还没跑通，先别急着提交"

print(check_milestone(True, True))
print(check_milestone(True, False))
```

> ⚠️ 新手最容易踩的坑：
> 1. **不备份 = 把项目交给运气**：AI 一次大改，可能删掉你辛苦做两天的活。
> 2. **提交不是越频繁越好**：要"能正常运行的阶段"才提交，不是每改一行就提交。
> 3. **推远程前检查「私有 / 公开」**：商业计划、Agent 宪法这些核心资产，别跟着代码一起公开。

## 🏃 小步快跑：先跑通最小版本再加功能

大厅墙上还贴着一句话：**小步快跑，先跑起来再升级**。管理员推来一辆自行车：先让车能骑，再装铃铛、车筐、车灯——而不是把配件全装齐再出发。

- **最小可用版本（MVP）**：先跑通一条最核心的线（比如"能登录"），哪怕丑、哪怕功能少
- **再一个功能一个功能加**：能登录 → 能发帖 → 能点赞……
- **大阶段拆成子阶段**：每完成一个子阶段，停下来**验收**，确认没问题再进下一站——这就是防漂移的节奏

用代码模拟"小步快跑"的版本推进：

```python
# 模拟：小步快跑，一个版本一个版本推进
versions = ["v1 最小版本：能登录", "v2 加功能：能发帖", "v3 加功能：能点赞"]
for v in versions:
    print("上线", v)
```

> ⚠️ 新手最容易踩的坑：
> 1. **一上来就要"全部功能"是烂尾的头号原因**：大而全 ≈ 永远做不完。
> 2. **别跳版本**：v1 还没跑通就急着做 v2，问题会越堆越多，最后推倒重来。
> 3. **每跑通一个版本先提交存档**，再动下一个——这样随时都能回到能跑的版本。
