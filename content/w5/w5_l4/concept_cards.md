# 运维与清理——让项目活得更久

## 🏰 运维日常：守卫塔的「巡夜」

**类比**：守卫塔建好、点灯上线，不是万事大吉——夜巡官每晚都要**巡夜**：翻一翻值班记录本（看日志）、查一查粮仓还够不够（做备份）、听一听哨声有没有异常（盯监控）。少巡一晚，塔里的火灭了、粮仓空了，可能天亮才发现。

项目上线也是这样。**能打开只代表「部署成功」；能不能一直稳定跑下去，才是上线之后真正要解决的事**。上线之后，你就是项目的夜巡官：

| 巡夜三件事 | 运维里的意思 | 比喻 |
| --- | --- | --- |
| 看日志 | 程序出事先翻记录，找 error/失败/超时 | 眼睛 |
| 做备份 | 数据定期存到别处，丢了能找回来 | 保命符 |
| 盯监控 | 服务挂了、硬盘满了、CPU 爆了，主动通知你 | 闹钟 |

**定义**：**运维** = 上线之后让项目「活得更久」的日常功夫。三件套：**看日志**（眼睛）、**做备份**（保命符）、**盯监控**（闹钟）。很多新人翻车，就是因为「上线那天庆祝完就再也不管」——等用户找上门才发现网站挂了几个小时，自己却一无所知。

```python
# 模拟夜巡官的「巡夜日报」：三个检查项逐条打勾
checks = {
    "看日志": "今早 9:00 有 3 条 error，已排查",
    "做备份": "凌晨 2:00 数据库备份完成，已存到异地的云存储",
    "盯监控": "CPU 45%，硬盘 62%，都在阈值内",
}
for item, detail in checks.items():
    print("✅", item, "→", detail)
```

> ⚠️ 易错点：
> 1. **上线不是终点**：项目能打开只是部署成功，「一直稳定跑」才是运维的本事。别上线那天庆祝完就再也不打开服务器——挂了、数据丢了、硬盘满了，你都得第一时间知道。
> 2. **备份有两条铁律**：备份不能和原数据放在同一块硬盘/同一台服务器上（被入侵或删除时备份会一起「陪葬」）；而且备份完一定要**真的演练一次恢复**——文件存在 ≠ 能恢复，等出事那天才发现备份用不了就晚了。

## 👀 看日志：运维的眼睛

**类比**：夜巡官靠塔里的**值班记录本**知道夜里发生了什么：谁来过、哪扇门响过、几点发生了什么。程序也一样——它会把自己运行的过程一条条记下来，这份记录就叫**日志**。程序出了事，第一件事就是翻日志。

**定义**：**日志** = 程序自己记的「流水账」，每跑一步记一行。**看日志** = 扫描日志里有没有**异常信号**：`error`（出错）、`失败`、`超时`、`内存`（内存不足）……找到这些词，就找到了问题出在哪一段。

```python
# 模拟一段日志：逐行扫描异常信号（error/失败/超时/内存）
log = """
10:00 启动守卫塔服务 成功
10:02 数据库连接 失败
10:05 响应 超时 1200ms
10:08 内存占用 95%
"""
for line in log.strip().split("\n"):
    t = line.lower()        # 统一小写，ERROR 大写也能查到
    if "error" in t or "失败" in t or "超时" in t or "内存" in t:
        print("⚠️ 异常信号 →", line)
```

> ⚠️ 易错点：
> 1. **大小写要对齐**：日志里可能是大写 `ERROR`，而你的关键词是小写 `error`——直接 `"error" in line` 会漏报。先把整行 `line.lower()` 转小写再匹配，大写小写都能查到。
> 2. **找到异常行只是开始**：别一看到 error 就慌，也别只盯着一行看。日志是按时间记的——**顺着时间顺序往前翻**，看这条异常之前发生了什么，才能找到真正的起因。

## 🧹 代码清理：上线前删掉「调试杂物」

**类比**：AI 帮你写功能时，会顺手留下一堆「临时用一下」的代码：调试用的打印、随手写的测试、写死的假数据、一次性脚本。功能做完了，这些代码的使命就结束了——可 AI 几乎不会主动删，它们就一块块堆在项目里，像**墓碑**一样。上线前，得把它们清掉。

**定义**：**代码清理** = 功能写完、测试通过、你确认没问题之后，删掉调试/临时验证用的临时代码。但清理不是见代码就删——先让 AI 交一份**清单**，标清楚每段代码当初干什么、现在删还是留；删完再跑一遍正式测试，确认正经功能都还在。

| 常见「墓碑代码」 | 该删 | 两样「长得像垃圾」但必须留 |
| --- | --- | --- |
| 调试打印（print 看看） | ✅ 删 | 正式的**回归测试**（保护网，每次改完都要重跑） |
| 临时测试接口 | ✅ 删 | 关键功能上的**运行日志**（上线后排查问题靠它） |
| 写死的假数据、一次性脚本 | ✅ 删 | |

```python
# 模拟「清理清单」：先让 AI 列出每段代码删还是留
items = [
    ("print(调试看数据)",         "调试打印",     "删"),
    ("测试接口 /test",            "临时测试接口",  "删"),
    ("写死的假用户",              "假数据",       "删"),
    ("test_order.py 回归测试",    "正式测试",     "留"),
    ("下单功能的运行日志",         "运行日志",     "留"),
]
for code, kind, action in items:
    print(action, "→", kind, "（", code, "）")
```

> ⚠️ 易错点：
> 1. **别误删保护网**：正式的回归测试（每次改完都要重跑的那套）和有意留在登录/下单/支付这些关键功能上的运行日志，和调试打印长得几乎一模一样——AI 一清理，最容易把它们**一锅端**。清理时话要说清楚：删的是临时调试，这两样得留。
> 2. **清理时机别搞反**：功能还没测过就急着删，调试工具没了反而耽误事。记住顺序：**功能写完 → 测试通过 → 你确认没问题 → 才清临时代码**；清完再跑一遍正式测试，确认没删坏东西。

## 🔍 改 bug 心态：定位，而不是重写

**类比**：守卫塔里一盏灯不亮了，你是先查灯泡、查线路，还是**把整座塔推倒重建**？当然是先定位——灯不亮可能只是灯泡坏了，推塔重建，塔里所有好好的房间也跟着一起没了。项目出问题也一样：**先定位问题在哪，别急着让 AI 重写整个项目**。

**定义**：**排障流程**四步走：**看日志**（找线索）→ **定位**（找到最早出错的位置）→ **修复**（改真正负责的代码）→ **验证**（重新跑一遍原过程，确认修好且没弄坏别处）。如果同一个 bug 让 AI 连续改**三轮**还没好（这叫「死亡循环」），就说明原因判断、修改位置、验证方法至少有一项错了——这时要**踩刹车**：停下修改、换一个新对话、翻出前三轮的记录，重新定位，而不是继续加补丁、更不是推倒重写。

```python
# 模拟排障四步：每步都做完，才宣布修好
steps = ["看日志，找线索", "定位最早出错的位置", "修复真正负责的代码", "重新运行，验证通过"]
for i, step in enumerate(steps, 1):
    print("第", i, "步 →", step)
```

> ⚠️ 易错点：
> 1. **「悄悄失败」≠ 修好**：AI 为了交差，可能用 try/except 把报错吞掉、把报错提示删掉——页面不报错了，但内部其实没跑成功。**页面不报错 ≠ 问题已解决**，验证要看真实结果，不能只看表面。
> 2. **别把「重写」当万能药**：重写会连已跑通的功能、数据关系、第三方接入一起丢掉，老问题还会原样跟到新项目里。只有定位确认问题出在「地基」这一层才值得重写——**先定位，再决定改哪里**，推倒重来永远是最后的手段。
