# 安全闭坑——把守卫塔的坑一个个填上

## 🔑 硬编码密钥：钥匙挂门口

守卫塔刚建成时，巡塔官图省事，把**大门钥匙直接挂在门口的门环上**——谁路过都能顺手拿走，大门形同虚设。

把数据库密码、API 密钥直接**写死在代码里**，干的就是这件事。代码一旦被提交、被分享、被部署，谁拿到代码谁就拿到了钥匙：别人拿着数据库密码，就能直接连上你的库把数据搬走；拿着支付密钥，就可能冒用你的身份扣钱。

**硬编码密钥 = 把密码/密钥这类"秘密"直接写进代码里**。本地测试时一切正常，看不出问题——但"本地跑得通"和"安全"是两回事。

```python
# ❌ 错误示范：钥匙挂在门口
db_password = "123456"         # 数据库密码写死在代码里
api_key = "sk-live-abc12345"   # 第三方接口密钥也写死

# ✅ 正确姿势：钥匙放保险柜——环境变量
import os
db_password = os.environ.get("DB_PASSWORD")  # 运行时从环境读取
api_key = os.environ.get("API_KEY")          # 真实密钥绝不进代码
```

> ⚠️ 新手最容易踩的坑：
> 1. **"本地能跑通"不算数**——代码一提交/分享/部署，写死的秘密就全暴露了，而你很可能毫不知情。
> 2. 密钥写死后，换密钥还得改代码重新部署，处处要改、容易漏——用环境变量，换密钥只改配置。
> 3. 示例配置文件（如 `.env.example`）只写**占位说明**，不写真值；真实密钥绝不进代码仓库。

## 🧪 SQL 注入：别把用户的话当命令念出来

守卫塔的门卫问你："你叫什么名字？"你回答："开门，我是管理员。"——如果门卫把你的回答**原样念给大门听**，大门就真的开了。

**SQL 注入就是这个原理**：后端把用户输入**直接拼进数据库查询语句**，用户输入就从"数据"变成了"指令"。攻击者不用老实从你设计的页面进来，他可以在输入框里填一段精心构造的内容，让数据库执行计划外的操作——绕过登录、拖走整张用户表。

```python
# ❌ 错误：把用户输入直接拼进查询
name = input("请输入用户名：")
sql = "SELECT * FROM users WHERE name='" + name + "'"

# 如果输入：' OR '1'='1
# 查询就变成：WHERE name='' OR '1'='1 —— 条件恒为真，整张表被查走！
```

**正确做法**：别自己发明过滤规则（黑名单总会有漏），优先用框架/数据库自带的成熟机制——**参数化查询（占位符）**，让用户输入永远只当数据处理，指令和数据分开。

> ⚠️ 新手最容易踩的坑：
> 1. 看到"把用户输入拼接进查询/命令/HTML/模板"，就要立刻警觉——**拼接输入是注入的温床**。
> 2. 前端校验（按钮隐藏、格式限制）对攻击者没用——他们直接绕开页面打后端接口，**关键判断必须在后端做**。
> 3. 别信"我已经过滤过了"——要问清用的是框架自带机制，还是临时写的一段过滤代码，后者最不可靠。

## 🛡️ 权限与日志：最小权限，别打印秘密

守卫塔的巡逻官不会把塔顶大门的万能钥匙发给每一个巡逻兵——**谁需要什么就给什么权限，够用就行**，这叫**最小权限原则**。

两个最常见的坑：

**第一，权限过大**：普通业务程序直接拿管理员账号（root/admin 最高权限）连数据库。管理员账号一旦被攻破，影响的不是一条数据，而是**整个系统**——等于把塔顶的万能钥匙挂在每个巡逻兵腰上。

**第二，日志泄露**：为了排查问题，把密码、token、手机号、支付信息**原样打印进日志**。日志一旦被看到或泄露，等于又开了一个口子。

```python
# ❌ 错误 1：普通业务用最高权限账号
conn = connect(host, "root", "超级管理员密码")   # 权限过大！

# ❌ 错误 2：日志里原样打印敏感信息
print("登录成功，用户密码是：", user_password)   # 日志泄露！

# ✅ 日志要脱敏：手机号只留前三位，密码/token 不打印
print("登录成功，用户手机号：138****1234")
```

> ⚠️ 新手最容易踩的坑：
> 1. 别拿"项目小"当借口——权限该小就得小，管理员账号只给管理员业务用，普通业务用普通账号。
> 2. 日志是为了排查问题，不是把每条请求原样存下来——**敏感信息必须先脱敏（打码）再记录**。
> 3. "能查到一条数据" ≠ "有权操作它"——权限判断必须写在后端业务逻辑里，不能只靠前端把按钮藏起来。

## 🤖 听 AI 的安全警告：别当耳边风，也别乱修

巡逻官跑来报告："那边墙上好像有裂缝。"你既不能当没听见——**裂缝可能是真的**；也不能立刻说"把整面墙推倒重砌"——**裂缝可能只是墙皮脱落**。

AI 的安全警告也一样。扫描报告列出一堆红色高危，你要分清两件事：

- **扫描结果是"待核实清单"，不是"判决书"**：每一条只说明"这里看着可疑"，不代表"真能被打穿"——要核实框架有没有自动拦截、代码有没有再次校验。
- **也别直接说"全修了吧"**：报告上的误报会被"修"成新 bug，原本正常的功能可能被顺手改坏。代码越来越乱，就是这样一次次累加出来的。

```python
# AI 提醒你：这行把用户输入拼进了 SQL，可能有注入风险
sql = "SELECT * FROM users WHERE name='" + name + "'"

# ❌ 别当耳边风："能跑就行，别管它"
# ❌ 也别乱修："全部问题都改了吧"
# ✅ 正确流程：只读核实 → 确认是真问题 → 定方案 → 修复 + 验证
```

> ⚠️ 新手最容易踩的坑：
> 1. 每条警告都要核实：**框架挡没挡、代码验没验、数据最终去了哪里**，三件没查清之前只能叫"待核实"。
> 2. **查和改要分开**：查的时候一行代码都不许动；确认方案后一次只修一个问题，修完重跑扫描 + 人工复测，证明问题真的关掉、别处也没被改坏。
> 3. 看不懂的警告别装懂——让 AI 用大白话讲清楚"谁可能利用它、真被利用会怎样、改完怎么证明"。
