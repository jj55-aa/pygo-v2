# 上线前审计——发射前的最后检查

## 🛂 上线前审计：守卫塔的「安检门」

守卫塔的城门下立着一道安检门：每位守卫出征前，都要把装备、行囊、通关文书一项一项过安检，全查完才放行。项目上线也一样——**不能代码一写完就直接上线**，上线前得过一次「安检」，把藏着的问题尽量揪出来，这就是**上线前审计（Pre-launch Audit）**。

审计到底查什么？记住四类要命的项：

| 类别 | 查什么 | 出事的后果 |
| --- | --- | --- |
| 功能 | 跑不跑得通？结果对不对？ | 用户用着用着就崩 |
| 安全 | 能不能越权看/改别人的数据？恶意输入会不会注入？ | 数据被偷、被改 |
| 数据 | 开发/生产环境分开没？测试数据混进真实数据没？ | 真实数据被搞脏、被误删 |
| 备份 | 万一出事，数据能不能恢复？ | 出事只能干瞪眼 |

判断优先级的标准很朴素：**这个功能一出错，会不会动到钱、权限、数据？** 会，就必须重点查；页面文案、颜色这类，错了顶多不好看，可以往后排。

用代码模拟一道安检门——把检查项一个一个过：

```python
# 模拟守卫塔安检门：上线前逐项检查
checks = ["功能测试", "安全扫描", "数据备份"]
for item in checks:
    print("检查中：", item, "...")
print("全部检查完成，可以放行！")
```

> ⚠️ 新手最容易踩的坑：
> 1. 审计不是「看着没问题」就放行——**要逐项核对真实结果**，不能凭感觉。
> 2. 别只查功能：安全、数据、备份这三类最容易出大事的项，恰恰是最多人漏掉的。

## 🔄 测试闭环：自己先跑一遍全流程

火箭发射前，工程师会先把全流程自己走一遍；飞行员起飞前，也会把整套动作在脑子里过一遍。上线前也一样：**别急着把活儿全甩给 AI，先自己当第一个用户，把核心流程从头到尾完整走一遍**——这就是**测试闭环**。

什么叫「闭环」？不是点一个按钮看它有没有反应，而是把一件完整的事**从头到尾严丝合缝地走完一整遍，最后结果还全对得上**。比如电商下单的闭环：

> 注册 → 登录 → 下单 → 支付 → 订单列表能看到这一单 → 状态显示「已支付」

这一长串连起来、结果对得上，才算走完了一个闭环。很多人只点到「下单」，看见屏幕弹出「下单成功」就以为成了——可钱到底扣了没有？库存真的减了吗？中间断一步，光看那个成功提示是发现不了的。

**「有反应」≠「结果对」**：页面提示成功，只代表动作有响应；真正要核对的是背后数据的变化——扣款金额对不对、库存数量减没减、订单状态变没变。AI 写的功能经常表面给个成功提示，底下的数字却算错了。

自己走，有三种走法，缺一条都算没走到位：

1. **走通主流程 + 核对结果**：把每条核心流程当真实用户从头走到尾，每个关键节点核对真实结果
2. **故意走歪路**：不登录就操作、该填数字的地方填 0/负数/超大数、输入框塞一堆特殊符号，看系统拦不拦
3. **检查被牵连的功能**：这次 AI 改了支付，就回头把下单、订单列表、退款、余额都点一遍——AI 改代码常「改一处、坏一处」，这个回头看的活只有你能做

用代码模拟一次「下单扣款核对」：

```python
# 模拟下单闭环中的关键一步：核对扣款结果
balance = 200
price = 100
balance = balance - price   # 模拟下单扣款
if balance == 100:
    print("扣款正确，闭环走通！")
else:
    print("扣款出错，禁止上线！")
```

> ⚠️ 新手最容易踩的坑：
> 1. 别满足于「有反应」：成功提示 ≠ 结果正确，要一项一项核对看不见的数据。
> 2. 别只测正常路径：边界值（0、负数、超大数）和非法输入，正是 bug 最爱藏的地方。

## 📋 自检清单：一项一项打勾

飞行员起飞前不会靠脑子回忆检查项，而是拿着一张 **checklist**，一项一项念、一项一项打勾，全部打勾才推油门。上线前也一样：把要查的事项写成一张**自检清单**，逐项核对判断（通过/不通过），没过的项先修完再上线。

清单的好处是**不靠记忆、不漏项**：功能、安全、数据、备份……每一项都有明确的判断标准，对着打勾就行。反过来，要是靠脑子记，忙起来最容易漏掉的就是那些「最要命」的项。

清单长什么样？守卫塔安检官手里那张就是：

| 检查项 | 判断标准 | 结果 |
| --- | --- | --- |
| 功能测试 | 核心流程走通且结果正确 | 通过 / 不通过 |
| 安全扫描 | 越权、注入、敏感信息泄漏都查过 | 通过 / 不通过 |
| 数据备份 | 数据已备份，出事能恢复 | 通过 / 不通过 |
| 性能测试 | 页面不卡、接口扛得住 | 通过 / 不通过 |

用代码把清单存下来，一项一项过：

```python
# 模拟自检清单：用字典记录每项的状态
checklist = {
    "功能测试": "通过",
    "安全扫描": "通过",
    "数据备份": "未通过",
}
for item, status in checklist.items():
    print(item, "：", status)
```

> ⚠️ 新手最容易踩的坑：
> 1. 清单要**写下来**，别凭脑子记——漏掉一项，可能就是上线后的一场事故。
> 2. 「未通过」的项必须**修完再上线**：带着病上线，一出事就是真实用户的数据和钱。

## ✅ 判题模拟：清单判断

安检官怎么决定放不放行？——逐项看状态，统计有没有「未通过」的项。这件事完全可以用代码模拟：**读入各检查项的状态，统计未通过项，据此给出「通过 / 还差几项」的结论**。

这就是本课 code 题的做法，也是守卫塔安检官的工作方式：

```python
# 模拟安检官：读入自检清单，统计未通过项
failed = []
n = int(input())          # 第一行：检查项数量
for _ in range(n):
    line = input()        # 每行格式：项名,是否通过
    name, status = line.split(",")
    if status == "未通过":
        failed.append(name)

if not failed:
    print("通过，可以上线！")
else:
    print("还差", len(failed), "项：" + "、".join(failed))
```

- `split(",")` 把「项名,状态」这一行拆成两项
- 状态等于「未通过」就记入 `failed` 列表
- 最后看 `failed` 是否为空：空 → 放行；不空 → 报出还差哪几项

> ⚠️ 新手最容易踩的坑：
> 1. 判断条件别写反：是 `if status == "未通过"`，不是 `== "通过"`——写反了会把没过的项当通过，放行一个不该放行的项目。
> 2. `split(",")` 里的逗号是**半角** `,`；如果输入行首尾有空格，先 `.strip()` 再去掉再判断。
